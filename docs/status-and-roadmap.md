# Статус и roadmap

Документ фиксирует текущее состояние проекта, известные проблемы и дорожную карту реализации фич. Обновлять после каждого значимого изменения.

## Текущее состояние

### Что работает

- Запуск: `BootSceene` → конфиги → `GameManager` → `TownHall`.
- Экономика: покупка шахтёра, пассивный доход (`update`), цена растёт по `priceMultiplier`.
- Клик-геймплей: `GoldNugget` (+1 золото) — работает в **Mine**; в **TownHall** самородок — индикатор количества золота (by design, тап не работает).
- Сохранение: инвентарь, рабочие, метка времени; загрузка с защитой от битых данных.
- Dev-консоль включает: открытие по `` ` ``, `reset`, `fps`, `scene`, `console` (работает; `addGold`/`setGold` — нет, см. P1).
- Сцены-заглушки не ломают переходы.

## Известные проблемы

### P1 — сломанные dev-команды
`BuiltinCommands.ts`:
- `addGold` → `GameManager.instance.addGold(amount)` — метода нет.
- `setGold` → `(GameManager.instance as any)._gold`, `.notifyScoreChanged()` — полей/метода нет (это старый API).

**Подтверждено запуском (27.10.2026):** в консоли `addGold 100` → `Failed: ...addGold is not a function`; `setGold 100` → `Failed: ...notifyScoreChanged is not a function`. Золото не меняется.

Следствие: команды падают (лог `Failed: …`), в UI золото не обновится.
**Рекомендация:** добавить в `GameManager` публичные `addGold(amount)` / `setGold(amount)` с использованием `Inventory.instance.add/set` и эмитом `RESOURCE_CHANGED`; убрать `as any`.

### P1c — доход 0.25/с отображается как «0»
`Utils.formatValue` при значениях < 1000 возвращает `Math.round(num)` → для `0.25` даёт `0`. Проверено запуском: `goldPerSecond = 0.25`, в UI `Income 0` (а `Workers 1`). Из-за этого доход до 1/с выглядит нулевым.

**Рекомендация:** для `0 < num < 1` показывать знаки после запятой (или форматировать по отдельному правилу).

### P2 — экономика шахтёра захардкожена
`assets/Script/model/units/Miner.ts:7-8`:
```ts
private _baseGoldPerSecond = 0.25;
private _defaultPrice = 10;
```
TODO-комментарии в `Miner.ts` и `Worker.ts` говорят о переносе в конфиги. Сейчас изменение баланса в `global-config.json` не влияет на доход (только на цену), `defaultPrice` вообще не используется логикой.

**Рекомендация:** добавить в конфиги `minerGoldPerSecond` / `minerBasePrice`, читать через `ConfigLoader` в `Miner` (или передавать из `GameManager`).

### P3 — оффлайн-доход без ограничений
`GameManager.processPostLoad()` (`GameManager.ts:136-143`) начисляет всё время `Date.now() - lastTimestamp`, без верхней границы.

**Риски:** подкрутка часов, «спящий» сейв со старым таймстампом → огромное количество золота.
**Рекомендация:** ограничить оффлайн-доход (например, `Math.min(diffSeconds, MAX_OFFLINE_SECONDS)`) или показывать игроку начисление.

### P4 — legacy / ивент-задел не подключён
`assets/Script/legacy/` — match-3 (Grid, Tile, BoardView, BlastGameManager, поведения, UIManager). **Осознанно сохранён** как основа для сюжетных ивентов. К игре не подключён. `assets/Scene/legacy/TapClapTest.fire` ссылается на скрипт с uuid `89e3cyvC9dGUrfoKqkdusTh`, которого нет среди текущих `.meta` (актуальный uuid `BlastGameManager` — `562d5478-…`).

**Не проблема сама по себе** — это технический долг для будущего этапа: при подключении ивентов потребуется ревизия/пересборка тестовой сцены и адаптация модулей под конфиги.

### P5 — прочее
- `Townhall.onDestroy` отписывает слушатель кнопки новым замыканием — реальная отписка не выполняется (не критично, т.к. сцена выгружается целиком, но паттерн неправильный).
- `GameManager.getNextWorkerPrice()` считает майнеров через `instanceof Miner` — при добавлении новых типов рабочих цену придётся дорабатывать.
- `ConfigParser` поддерживает только `NUMBER`; другие типы не парсятся — блокирует конфиг-драйвен фич.
- `Inventory.has()` и `updateGold` залогированы очень щедро (`cc.log` на каждый вызов) — в релизе замусорит консоль.
- Название в `project.json` — «HelloWorld»; `BootSceene` — опечатка (см. `docs/development.md`).

## Roadmap реализации фич

Порядок этапов выбран так, чтобы сначала укрепить фундамент (конфиги, сохранение, события), затем добавить контент-платформы (диалоги, события-сцены), и только потом — полный сюжетный контур.

### Этап 0. Фундамент и стабилизация базы (текущее)

**Цель:** игра стабильно работает, тесты баланса удобны.

- [x] Документация: README + docs/*
- [ ] P1: починить `addGold`/`setGold` + убрать `as any`
- [ ] P1c: форматирование дробного дохода (`Utils.formatValue`)
- [ ] P2: вынести экономику шахтёра в конфиги (`minerGoldPerSecond`, цена)
- [ ] P3: ограничить оффлайн-доход (максимум `MAX_OFFLINE_SECONDS` или UI-подтверждение)

**Критерии приёмки:** dev-команды работают, доход отображается корректно, баланс редактируется в JSON, оффлайн-доход ограничен.

### Этап 1. Конфиг-платформа

**Цель:** заменить жесткую `ConfigData`/`ConfigParser` на универсальный, типизированный слой конфигов; ввести реестры.

- [ ] Расширить `ConfigParser`: `number | string | boolean | enum | string[] | вложенные конфиги`
- [ ] Универсальный `ConfigLoader` по типам (`BaseConfigLoader<T>`, `getAll`, `getById`)
- [ ] Проверка конфигов на этапе загрузки (имя файла + поле в ошибке)
- [ ] Реестры: `workers.json` (параметры рабочих), `buildings.json` (здания)
- [ ] Легковесная валидация «лишнего поля» (опция) и fallback-значения

**Критерии приёмки:** новый тип конфига добавляется без правки `ConfigParser`-магистрали (только описание типа), ошибки понятны, конфиги подхватываются `ConfigLoader`.

### Этап 2. Сохранение и прогресс

**Цель:** сохранять состояние, выходящее за рамки «инвентарь+рабочие».

- [ ] `SaveData`-реестр: прогресс города, сюжетные точки (`storyPointId`), `flag`-ы, прогресс ивентов
- [ ] Версионирование сейва и миграции
- [ ] Атомарная запись/чтение (защита от повреждения JSON)
- [ ] Хранилище ключей в одном месте (`SaveManager`)
- [ ] Dev-команды: посмотреть/сбросить конкретные ключи

**Критерии приёмки:** после рестарта сохраняются город, сюжетные точки, флаги; старый сейв мигрирует без потерь; повреждённый сейв не валит игру.

### Этап 3. Диалоговая система

**Цель:** простой, конфиг-управляемый фреймворк диалогов (2 портрета + текст).

- [ ] `DialogConfig` + `dialogues.json`
- [ ] `DialogueUI` (портреты слева/справа, центральный текст) и `DialogueSystem` (очередь, `DIALOGUE_FINISHED`)
- [ ] Запуск из сцены и из ивента; поддержка «Далее» и зигзага «говорящий»
- [ ] Портреты/тексты по ключам; локализуемые строки
- [ ] Dev-команда `dialog <id>`

**Критерии приёмки:** диалог полностью описывается JSON; запускается из любой сцены; в `cc`-превью видно 2 портрета и текст; завершение даёт событие.

### Этап 4. Сюжетные триггеры и менеджер ивентов

**Цель:** декларативно описывать, когда что запускается.

- [ ] `StoryManager`: условия (`resource`/`progress`/`storyPoint`/`event`) + проверка после изменений
- [ ] `story.json` — описание точек: `trigger → dialog → event → onComplete`
- [ ] `EventManager`: старт (загрузка сцены ивента), результат (награда/прогресс), возврат в `TownHall`
- [ ] `StoryController` — очередь/разрешение «может ли ивент начаться, если уже открыт другой»
- [ ] Dev-команда `story <pointId>` / `event <eventId>`

**Критерии приёмки:** сюжетная точка описывается в JSON; при достижении условия открывается диалог → ивент; награды/флаги сохраняются; повторные срабатывания исключены.

### Этап 5. Динамические сцены ивентов (Match-3 / Blast)

**Цель:** одна универсальная сцена ивента, собираемая из конфига, минимум 2 механики.

- [ ] `EventScene.fire` — универсальный контейнер (фон, UI-слои, результат/кнопки)
- [ ] `EventSceneManager`/`ModuleLoader` по `eventId`
- [ ] `Match3Module`: адаптация `legacy/` (Grid, BoardView, CommonBlast, Bomb, behaviors) под конфиг (тайлы, правила, победа/поражение)
- [ ] `BlastModule`: адаптация blast-механик legacy под конфиг
- [ ] Победа/поражение → `onComplete` из `story.json` (награды, unlock)
- [ ] Конфиги: `events/*.json` + черновик из `docs/configs.md`

**Критерии приёмки:** ивент целиком описан в JSON; два разных ивента (match3/blast) с разными тайлами/условиями запускаются на одной сцене; после завершения — корректный результат и сохранение.

### Этап 6. City Builder

**Цель:** расширить основную петлю до «покупка зданий → эффекты на базу».

- [ ] Модель зданий (`buildings/`), `BuildingFactory` (по конфигу)
- [ ] `Buildings`-сцена: список зданий, стоимость, кнопки «построить»
- [ ] `BuildingEffect` (доход-множители, лимиты, разблокировки)
- [ ] Отражение эффектов в `GameManager` (глобальный `incomeMultiplier`)
- [ ] Сохранение/загрузка города; конфиги `buildings.json`

**Критерии приёмки:** здание строится из JSON-описания, эффект применяется к доходу/стоимости, город сохраняется и восстанавливается.

### Этап 7. Сюжетный контур и контент

**Цель:** связать всё в законченный вертикальный срез.

- [ ] Сквозной сценарий: первые N сюжетных точек (диалоги → ивенты → награды → разблокировки)
- [ ] Тест-контент: 2 ивента (match3 + blast), 2–3 диалога, 3–4 здания
- [ ] Баланс: цены, доходы, награды (через конфиги, без кода)
- [ ] UI-фидбек: уведомления о награде/открытии, индикаторы сюжетных точек
- [ ] Ручной прогон «0 → новый игрок → сюжетная точка полного цикла»

**Критерии приёмки:** новый игрок проходит прототип от базы до ивента без правок кода; контент правится в JSON.

### Этап 8. Полировка и релиз-готовность

- [ ] Локализация строк (ключ → ресурс)
- [ ] Оптимизация логов, уборка неиспользуемых событий (`SCORE_CHANGED`, `BUILDINGS_LOADED`)
- [ ] Ревизия `legacy/TapClapTest.fire` (убрать/починить ссылки)
- [ ] Инструмент валидации конфигов (скрипт/CI)
- [ ] Документация гейм-дизайнера: «как добавить ивент/диалог/здание»

**Критерии приёмки:** конфиги валидируются автоматически, документация гейм-дизайнера есть, лог-шум минимален.

## Зависимости и риски

| Зависимость | Что зависит |
| --- | --- |
| Расширение `ConfigParser` (Этап 1) | Этапы 3–6 (диалоги, ивенты, здания) |
| Версионированное сохранение (Этап 2) | Этапы 4, 6 (сюжет/город) |
| `Legend` legacy-модулей | Этап 5 (адаптация match-3/blast) |
| Модель зданий/эффектов | Этап 6 (город) |

| Риск | Митигация |
| --- | --- |
| Legacy-код имеет свои зависимости (uuid, свойства в `@property`) | Пересобрать/перепривязать в редакторе, завести отдельную тестовую сцену |
| Перегруженный `ConfigParser` | Итеративно: сначала нужные типы, потом обобщение |
| Рост JSON по мере контента | Реестр + отдельные файлы ивентов; валидатор |
| Одновременно идущие диалоги/ивенты | Очередь/блокировка через `StoryController` |
